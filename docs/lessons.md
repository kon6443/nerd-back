> **용도**: 사용자 교정·발견된 실수·사후 분석 직후 항목을 **추가(append)** 한다.

## 2026-08-27 — 실측 카운트를 손으로 세면 규약 문서가 스스로를 배신한다

- **실패 양상**: `code-patterns.md` §10 이 "로컬 TZ 의존 메서드 **18종**을 린트로 막는다"고 적었는데 실제 `eslint.config.mjs` 정규식의 대안은 **19종**이었다. 이 저장소의 규약 문서는 "실측 카운트 병기"를 규율로 삼는데, 정작 그 카운트가 틀려 있었다. 같은 절의 "린트가 error 로 막는다"도 **예외 3곳이 빠져** 있어(목록은 [`.claude/rules/code-patterns.md`](../.claude/rules/code-patterns.md) §10 이 SSOT), spec 에서도 막힌다고 오독할 수 있었다.
- **탐지 신호**: 사람이 눈으로 세면 맞아 보인다. 정규식 대안을 **프로그램으로 split 해 길이를 출력**하자 즉시 드러났다 — `s.match(...)[1].split('|').length` → 19. 리뷰에서 "카운트 주장"을 만나면 그 자리에서 재집계하는 것 외에 탐지 수단이 없다.
- **근본 원인**: 카운트가 **작성 시점의 수동 집계**였고, 이후 검산 경로가 없었다. 규약 문서의 숫자는 코드가 바뀌면 조용히 썩는데, 틀린 숫자도 "실측했다"는 형식을 갖추고 있어 신뢰돼 버린다. 예외 범위 누락도 같은 원인이다 — 룰의 `files` 오버라이드를 읽지 않고 상위 선언만 옮겨 적었다.
- **예방 규칙**: **규약 문서에 숫자를 쓸 때는 그 숫자를 뽑은 명령을 함께 남기거나, 최소한 프로그램으로 세서 쓴다.** 눈으로 센 숫자는 쓰지 않는다. 린트·설정을 인용할 때는 **상위 선언과 `files`/`overrides` 예외를 같이 확인**하고, 예외가 있으면 반드시 병기한다("무엇이 막히는가"만큼 "어디서 안 막히는가"가 중요하다). 카운트 병기 옆에 확인일을 남긴다.

## 2026-08-26 — 시크릿은 "설정했다"가 아니라 "파싱된다"를 확인해야 한다

- **실패 양상**: 첫 배포에서 두 워크플로가 동일하게 `ssh.ParsePrivateKey: ssh: no key found` → `handshake failed: attempted methods [none]` 으로 실패했다. 시크릿 9개를 다 등록했는데도 SSH 인증 수단이 하나도 없는 상태로 접속을 시도했다.
- **탐지 신호**: 같은 로그에 `remote server os type is unix` 가 함께 찍혔다. **호스트에는 도달했다는 뜻**이므로 host·user 시크릿은 정상이고 키 값만 문제라는 것이 이 한 줄로 좁혀졌다. `no key found` 는 "값이 틀렸다"가 아니라 **PEM 블록 자체를 못 찾았다**는 뜻이라, 공개키를 넣었거나 줄바꿈이 깨졌거나 비어 있는 경우다.
- **근본 원인**: 시크릿은 write-only 라서 등록 후 값을 다시 읽어 검증할 수 없다. "붙여넣었다"와 "파싱 가능한 형태로 들어갔다"가 다른데, 확인 수단이 배포 실패뿐이었다.
- **예방 규칙**: 키를 시크릿에 넣기 **전에** 로컬에서 그 키로 실제 접속을 검증한다 — `ssh -i <키> <user>@<host> 'echo ok'`. 복사는 드래그하지 말고 `pbcopy < <키파일>` 로 한다(줄바꿈 보존). 그리고 인증 실패 로그를 읽을 때 **어디까지 성공했는지**를 먼저 본다: 호스트 도달 여부가 찍혀 있으면 원인 범위가 절반으로 준다.

## 2026-08-26 — 외부 의존이 끊기면 트래픽 0에서도 로그가 쌓인다

- **실패 양상**: Redis 가 죽은 상태에서 **요청을 하나도 안 보내도** 60초에 29줄이 찍혔다. 하루 41,760줄/레플리카, 레플리카 3개면 **125,280줄/일**. 로그 수집 스택이 공유 자원이고 인제스트 한도가 낮아, 남의 로그 조회까지 느려질 양이었다. 별도로 readiness 는 같은 실패를 2줄로 중복 기록했다(Terminus 의 error + 우리 필터의 warn).
- **탐지 신호**: 코드 리뷰로는 안 보인다. `client.on('error', ...)` 한 줄은 정상적인 코드다. **컨테이너를 띄우고 요청 0건으로 유휴 상태를 재본 뒤에야** 드러났다. "요청당 몇 줄"만 보면 배경 노이즈를 놓친다.
- **근본 원인**: ioredis 는 끊긴 동안 약 2초 간격으로 재연결을 시도하고 매번 `error` 이벤트를 낸다. 이벤트 핸들러에서 바로 로그를 찍으면 **이벤트 발생 빈도가 곧 로그 발생 빈도**가 된다. 중복 기록은 "라이브러리가 이미 로그를 찍는가"를 확인하지 않은 탓이다.
- **예방 규칙**: 재시도·재연결하는 외부 의존의 이벤트 핸들러는 **반드시 `createLogThrottle` 로 감싼다** — 첫 발생은 즉시, 이후는 간격 제한 + 억제 건수 보고. 그리고 로그를 추가할 때 **라이브러리가 같은 이벤트를 이미 찍는지 확인**한다. 검증은 요청 0건 유휴 측정으로 한다: 컨테이너를 띄우고 60초 대기 후 로그 증가량을 센다. 수정 후 29줄 → 1줄(96.6% 감소), readiness 는 요청당 2줄 → 1줄.

## 2026-08-26 — 데코레이터의 기본 인자가 우리 설정과 맞지 않았다

- **실패 양상**: 헬스체크 컨트롤러에 `@SkipThrottle()` 을 붙였는데 레이트리밋이 그대로 적용됐다. 컨테이너를 띄워 측정한 결과 health 5회 요청에 스토리지 접근이 5회 발생했다. Redis 가 죽은 상태에서는 폴링마다 fail-open 경고가 찍혀, 15초 간격 × 레플리카 3개 = 하루 약 1.7만 줄이 공유 로그 스택으로 나갔을 상황이었다.
- **탐지 신호**: 컨테이너 로그에 `CustomThrottlerGuard` 경고가 `/api/v1/health` 요청과 함께 찍힘. **코드만 읽었을 때는 아무 문제가 없어 보였다** — 데코레이터가 붙어 있으니 동작한다고 넘어갈 자리였다.
- **근본 원인**: `SkipThrottle(skip = { default: true })` 은 `THROTTLER_SKIP + 'default'` 키에 메타데이터를 쓰지만, 가드는 `THROTTLER_SKIP + <throttler 이름>` 을 조회한다. 우리 throttler 이름이 `short`·`long` 이라 `default` 키는 아무것도 매칭하지 않는다. **라이브러리 기본값이 "이름 없는 throttler 하나" 를 가정하는데 우리는 이름을 붙여 두 개를 쓴 것**이 어긋난 지점이다.
- **예방 규칙**: 데코레이터·설정의 **기본 인자가 우리 구성을 가정하고 있는지** 확인한다. 특히 이름·키로 매칭되는 API 는 양쪽 이름이 실제로 같은지 본다. 그리고 "붙였으니 된다" 를 코드 리뷰로 끝내지 않고 **계측 지점을 만들어 숫자로 확인한다** — 지금은 스토리지 호출 횟수를 세는 E2E 로 고정했고, 방어를 걷어내면 0 → 10 으로 깨지는 것까지 확인했다.

## 2026-08-26 — 같은 스택에 묶으면 배포 수명주기가 붙는다

- **실패 양상**: 앱과 Redis 를 한 스택에 두고 "Swarm 은 스펙이 바뀐 서비스만 갱신하므로 앱 배포가 Redis 를 재시작하지 않는다"고 판단했다. 이 방향은 맞았지만 **반대 방향을 놓쳤다** — Redis 설정만 바꿔도 커밋 SHA 가 바뀌어 앱 이미지 태그가 달라지므로 앱 서비스 스펙도 변경되고, 결과적으로 이미지 빌드부터 앱 재배포까지 전부 돈다.
- **탐지 신호**: "A 를 바꿨는데 B 도 배포되나?"를 **양방향으로** 물어봤을 때 한쪽만 답이 나오는 상태. 그리고 이미지 태그가 커밋 SHA 인 구조에서는 "스펙이 안 바뀐다"는 가정이 거의 항상 깨진다.
- **근본 원인**: 서비스 이름을 예쁘게 만들려고(`prod_nerd_redis`) 스택을 공유했다. **표시상의 이점을 위해 운영상의 결합을 받아들인** 것이다. 참고 프로젝트는 인프라를 별도 스택 + 별도 워크플로로 두고 있었는데 그 이유를 늦게 파악했다.
- **예방 규칙**: 배포 단위를 나눌 때는 **"무엇을 바꿨을 때 무엇이 재배포되는가"를 표로 먼저 그린다.** 이름의 미관은 그 표보다 뒤다. 지금은 스택을 분리하고 그 표를 README 에 못박았다.

## 2026-08-26 — Swarm 서비스 DNS 이름을 스택 이름과 혼동했다

- **실패 양상**: 스택을 `prod_nerd_back`, 서비스를 `app` 으로 정의해 실제 서비스 DNS 가 `prod_nerd_back_app` 이 되는데, 배포 스모크 테스트와 리버스 프록시 설정은 `prod_nerd_back` 을 가리키고 있었다. 배포하면 스모크 테스트가 무조건 실패하고, 프록시는 업스트림을 못 찾는다.
- **탐지 신호**: 코드·설정 어디에도 에러가 없다. **배포해 봐야 드러나는** 종류다. 발견은 Redis 서비스를 추가하려고 이름 구조를 다시 따져보다 나왔다.
- **근본 원인**: Swarm 서비스 DNS 는 **`<스택명>_<서비스명>`** 이다. 원하는 이름을 스택 이름에 넣으면 서비스 키가 뒤에 한 번 더 붙는다. compose 파일만 보면 서비스 키가 `app` 이라 최종 이름이 눈에 보이지 않는다.
- **예방 규칙**: 스택·서비스 이름을 정할 때 **최종 DNS 이름을 먼저 적고** 거기서 역산한다. 지금은 스택 `prod_nerd` + 서비스 `back` → `prod_nerd_back`, 스택 `prod_nerd_cache` + 서비스 `redis` → `prod_nerd_cache_redis` 로 잡았다. 이름을 참조하는 곳(스모크 테스트·프록시 설정·`docker service ps`)은 한 군데서 정의한 값을 쓰도록 문서에 명시한다.

## 2026-08-26 — 전역 에러 필터가 헬스체크 진단 결과를 덮어썼다

- **실패 양상**: readiness E2E 가 `details.redis.status = 'down'` 을 기대했는데 응답이 `{ code: 'SERVICE_UNAVAILABLE', message: 'Service Unavailable Exception', timestamp }` 로 왔다. 어느 의존이 왜 죽었는지가 통째로 사라졌다.
- **탐지 신호**: 503 은 맞는데 본문에 진단 정보가 없음. 상태코드는 정상인데 페이로드만 비어 보이는 형태.
- **근본 원인**: Terminus 는 검사 실패를 `ServiceUnavailableException` 으로 던지는데, **그 응답 본문이 진단 결과 그 자체**다. 전역 `HttpExceptionFilter` 가 "모든 예외를 하나의 형식으로 통일한다"는 규칙을 예외 없이 적용해 그 본문을 버렸다. 규칙 자체는 옳지만 **적용 범위를 좁히지 않은 것**이 문제였다.
- **예방 규칙**: 전역 필터·인터셉터를 만들 때 **"이 규칙이 적용되면 안 되는 응답이 있는가"** 를 먼저 확인한다. 지금은 `status` 와 `details` 를 모두 가진 페이로드를 통과 대상으로 좁혀 처리했고, 그 동작을 단위 테스트로 고정했다. 응답 형식을 바꾸는 전역 장치는 반드시 통과 케이스를 함께 테스트한다.

## 2026-08-26 — 로컬 빌드 성공이 컨테이너 빌드 성공을 뜻하지 않는다

> 겪기 전에 선등재한 항목. 참고 프로젝트에서 실제로 발생해 CI 가 5일간 깨져 있었던 사례다.

- **실패 양상**: 로컬 `pnpm build` 는 계속 통과하는데 컨테이너 빌드만 `error TS5058: The specified path does not exist: 'tsconfig.build.json'` 으로 실패한다. `tsconfig.build.json` 을 도입하고 `build` 스크립트를 바꿨는데 `Dockerfile` 의 `COPY` 목록을 함께 갱신하지 않은 경우다.
- **탐지 신호**: 로컬은 통과하는데 CI 만 실패. `tsc` 가 **설정 파일 자체를 못 찾는** 에러(TS5058)는 타입 오류가 아니라 **입력 파일 집합의 차이**를 가리킨다.
- **근본 원인**: 로컬 빌드의 입력은 **레포 전체**지만 컨테이너 빌드의 입력은 **`COPY` 로 명시한 것뿐**이다. 두 입력 집합이 다르므로 로컬 통과가 컨테이너 통과를 보증하지 않는다. `tsconfig.build.json` 은 `tsconfig.json` 을 extends 하므로 두 파일이 모두 필요하다.
- **예방 규칙**: 빌드 **진입 설정**(`tsconfig*.json`, `build` 스크립트, 엔트리 경로)을 바꾸면 같은 커밋에서 `Dockerfile` 의 `COPY` 목록을 확인한다. `pnpm ci:all` 은 이 종류를 잡지 못한다(레포 전체를 입력으로 쓰므로). 그래서 **CI 에 ARM64 이미지 빌드 검증을 별도 job 으로 넣었다.** `Dockerfile` 의 COPY 블록에는 각 파일이 왜 필요한지 주석으로 남긴다.

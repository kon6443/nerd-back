# 실사 임시 보관 및 사용자 데이터 삭제 명세

> 작성일: 2026-09-18 · 상태: **정책 확정 · 구현 대기**
> 상위 문서: [`tasks-my-story.md`](tasks-my-story.md)

---

## 1. 목적과 적용 범위

사용자가 촬영·첨부한 **실사 정면 사진**은 동화 생성에 필요한 기간에만 자체 오브젝트 스토리지에 보관한다. 책 삭제 또는 회원 탈퇴 시에는 그 사용자의 개인 데이터와 개인 오브젝트를 제거한다.

이 문서는 `DIRECT_FACE_MODE=true`를 계속 지원하면서도 실사 원본을 영구 보관하지 않기 위한 구현 기준이다. DB에는 이미지 바이트나 base64를 저장하지 않고 오브젝트 키만 저장한다.

## 2. 데이터 분류와 보관 위치

| 분류 | DB 필드/키 | 오브젝트 위치 | 보관 규칙 |
|---|---|---|---|
| 실사 원본 | `sourcePhotoKey` (nullable) | `temp/source-photo/{sessionId}/{uuid}.{ext}` | 페이지 생성 중에만 보관. 완료 즉시 삭제, 24시간 TTL은 안전망 |
| AI 주인공 레퍼런스 | `referenceImageKey` (nullable) | `references/{sessionId}/{uuid}.{ext}` | 개인 생성물. 책 삭제·탈퇴 시 제거 |
| 개인화 삽화 | `session_page_images.imageKey` | 기존 개인 세션 prefix | 개인 생성물. 책 삭제·탈퇴 시 제거 |
| 캐릭터 답변 음성 | `story_page_chats.replyAudioKey` | `chat-audio/{sessionId}/...` | 개인 생성물. 책 삭제·탈퇴 시 제거 |
| 공유 템플릿·낭독 자산 | 템플릿/페이지 키 | `templates/...` 등 | 사용자 데이터가 아니며 삭제 대상에서 제외 |

`sourcePhotoKey`와 `referenceImageKey`는 의미와 저장 위치를 반드시 분리한다. 특히 직접 얼굴 모드의 실사 원본을 `references/`에 저장하거나 `referenceImageKey`에 넣지 않는다.

## 3. 실사 원본 처리 규칙

1. 브라우저는 촬영·선택한 파일을 `Blob`과 미리보기 object URL로만 일시 보유한다. 교체·제출 성공·화면 이탈 시 object URL을 해제한다.
2. 백엔드는 multipart 수신 버퍼를 요청 메모리에서만 검증·처리한다. 서버 디스크, DB blob/base64, 로그, 오류 보고, APM에 원본 바이트·base64·원본 키를 남기지 않는다.
3. `DIRECT_FACE_MODE=true`이면 원본을 `temp/source-photo/`에 업로드하고 `sourcePhotoKey`만 저장한다. 페이지 생성은 이 객체를 내부적으로 읽어 사용한다.
4. `DIRECT_FACE_MODE=false`이면 원본을 AI 레퍼런스 생성에 사용한 뒤 요청 메모리에서 폐기한다. 생성된 AI 레퍼런스만 `references/`와 `referenceImageKey`에 저장한다.
5. 임시 원본에는 어떤 API도 서명 URL 또는 직접 접근 URL을 발급하지 않는다. 버킷은 비공개이며, 백엔드의 권한 확인을 거친 내부 처리만 읽을 수 있다.
6. 사진을 다시 올리면 새 업로드가 DB에 연결된 뒤 이전 `sourcePhotoKey`를 삭제한다. 이전 객체 삭제가 실패하면 영속 정리 작업에 넣는다.
7. Redis·AOF·Redis 볼륨에는 실사 원본 바이트를 저장하지 않는다. Redis는 정리 작업의 잠금·중복 방지 같은 작은 메타데이터에만 사용한다.

`temp/source-photo/`는 사용자 브라우저 메모리나 서버 RAM 경로가 아니라 **오브젝트 스토리지의 키 prefix**다. 실제 파일은 MinIO/S3에 존재하되 임시 수명 정책을 적용한다.

## 4. 완료·실패·TTL 수명주기

```text
사진 수신 → temp/source-photo/ 업로드 → 페이지 생성/재시도
                                         ├─ 전체 완료 → 즉시 객체 삭제 → sourcePhotoKey 비움
                                         └─ 실패/중단 → 재시도 가능 기간 유지 → TTL 만료 시 자동 삭제
```

- 모든 페이지 생성이 완료되면 원본 객체를 즉시 삭제하고 `sourcePhotoKey`를 `NULL`로 갱신한다. TTL을 정상 삭제 수단으로 사용하지 않는다.
- 스토리지 삭제 실패, 교체 중 이전 키 삭제 실패, 업로드 후 DB 갱신 실패는 **영속적인 정리 작업**에 기록한다. 작업은 멱등적으로 재시도하며, 단순 경고 로그만 남기고 고아 객체를 방치하지 않는다.
- `temp/source-photo/` prefix에만 24시간 lifecycle expiry를 인프라로 설정한다. `references/`, 페이지 삽화, 음성, 공유 자산에는 이 규칙을 적용하지 않는다.
- TTL로 원본이 먼저 사라진 뒤 생성 재시도가 필요하면, 기존 사진을 찾으려 하지 않고 사용자에게 사진을 다시 올리도록 안내한다.
- 세션 삭제와 비동기 페이지 생성·TTS가 경합할 때 새 개인 오브젝트가 남지 않도록, 삭제 진행 중인 세션에는 새 작업/업로드를 막고 생성된 키는 정리 작업에 포함한다.

## 5. 책 삭제와 회원 탈퇴

책 삭제는 해당 세션의 DB 레코드뿐 아니라 다음 개인 키를 모두 수집해 삭제한다.

- `sourcePhotoKey`
- `referenceImageKey`
- 모든 `session_page_images.imageKey`
- 모든 `story_page_chats.replyAudioKey`

회원 탈퇴는 사용자가 소유한 모든 세션에 위 규칙을 적용하고, 정리 작업이 추적 가능한 상태에서 계정·인증 상태를 제거한다. DB의 FK cascade는 오브젝트 스토리지를 지우지 않으므로 스토리지 키 수집·삭제를 별도로 구현해야 한다. 공유 템플릿, 기본 삽화, `story_pages.narrationAudioKey` 같은 공용 자산은 절대 삭제하지 않는다.

오브젝트 삭제와 DB 삭제는 하나의 트랜잭션이 될 수 없으므로, 사용자가 삭제한 데이터에 더 이상 접근할 수 없게 하는 DB 처리와 스토리지 정리를 영속 작업으로 연결한다. 삭제 실패는 재시도·관측 대상이며, 성공으로 위장하지 않는다.

## 6. 외부 처리와 접근 통제

- 일반 모드의 레퍼런스 생성과 직접 얼굴 모드의 페이지 생성은 실사 원본을 외부 이미지 제공자(OpenRouter 등)로 전송할 수 있다. 이는 자체 스토리지 보관과 별개의 처리이며, 제공자의 보관·학습 정책 확인 및 사용자 고지 범위로 관리한다.
- 실사 원본, 임시 키, 실제 세션의 서명 URL은 응답 본문·애플리케이션 로그·오류 추적 도구에 노출하지 않는다. 운영 진단에 세션 식별자가 꼭 필요하면 최소화 또는 마스킹한다.
- 책 삭제·탈퇴 API와 임시 객체 조회 경로 모두 소유자 인증·인가를 적용한다.

## 7. 구현 수용 기준

- [ ] 직접 얼굴 모드의 원본은 `temp/source-photo/`와 `sourcePhotoKey`에만 존재하며 `references/`와 `referenceImageKey`에는 AI 레퍼런스만 저장된다.
- [ ] 완료 시 원본 객체가 즉시 삭제되고 DB 키도 비워진다. 삭제 오류와 중복 삭제는 영속 작업으로 멱등 재시도된다.
- [ ] 업로드 후 DB 저장 실패, 사진 교체, 세션 삭제 중 생성 실패에서도 개인 오브젝트가 고아로 남지 않는다.
- [ ] lifecycle 규칙은 `temp/source-photo/`에만 24시간으로 적용되며, TTL 만료 뒤 재시도는 재촬영 안내를 제공한다.
- [ ] 책 삭제와 회원 탈퇴가 실사 원본·AI 레퍼런스·개인화 삽화·답변 MP3를 모두 수집해 제거하고 공유 낭독/템플릿 자산은 보존한다.
- [ ] 임시 원본 URL을 API가 발급하지 않고, 타 사용자도 접근할 수 없다. 로그·응답·오류에 원본 바이트/base64/원본 키가 없다.
- [ ] 삭제와 페이지 생성·TTS의 경합, 권한 위반, 삭제 작업 재시도를 자동 테스트한다.

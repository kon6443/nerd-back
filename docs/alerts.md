**등급이 곧 행동 시급도다.** 🔴 는 지금 봐야 하고, 🟠 는 반복되면 봐야 하고, 🔵 는 나중에 대조할 때 쓴다.

### 기동 알림에 담기는 것

```
🔵 백엔드 기동
요청을 받을 준비가 끝났습니다.
환경: production   레플리카: #2   버전: a1b2c3d
```

- **레플리카 번호**는 Swarm 의 `{{.Task.Slot}}` 이다(`infra/prod_nerd_back.yml`). 3개가 롤링으로 교체되므로 **세 건이 순차로** 온다 — 하나만 오면 나머지가 못 뜬 것이다.
- **버전**은 이미지 태그(커밋 SHA). `image:` 가 쓰는 변수와 같은 값이라 두 곳이 어긋날 수 없다.
- 로컬에는 슬롯도 버전도 없어 `레플리카: #1` · 버전 필드 생략으로 나간다.

## 설정

| 환경 | 파일 | 키 |
|---|---|---|
| 로컬 | `apps/back/.env` | `DISCORD_WEBHOOK_URL` |
| 서버 | `<DEPLOY_DIR>/env/prod_nerd_back.env` | 같음 |

- **백엔드 전용이다.** 프론트에 넣지 않는다 — 브라우저 번들에 박혀 URL 이 공개된다.
- 🚫 **값을 저장소·로그·응답 어디에도 남기지 않는다.** webhook URL 은 그 자체가 인증 수단이라, 아는 사람은 누구나 그 채널에 글을 쓸 수 있다.
- **비우면 알림이 전부 꺼진다**(`NoopNotificationAdapter`). 이것이 롤백 경로다 — 알림이 시끄러우면 코드를 되돌리지 않고 env 만 비운다.
- 서버는 env 변경 후 **스택 재배포**가 필요하다(컨테이너 재생성 시점에 읽는다).

## 무엇을 알리고 무엇을 알리지 않는가

### 원칙 — 「사람이 지금 행동해야 하는가」

이 질문에 **아니오**면 로그로 간다. 이 선을 넘기면 **알림 피로**가 오고, 사람이 알림을 읽지 않게 되어 **진짜 장애를 놓친다.** 알림은 많을수록 좋은 것이 아니라, 많아질수록 쓸모가 없어진다.

모든 알림은 네 가지를 답해야 한다 — **무엇이 / 어디서 / 얼마나 / 다음에 무엇을 해야 하는가.**

### 보낸다

| 등급 | 무엇 | 왜 |
|---|---|---|
| P0 | 비용·쿼터 소진 | 결제 전까지 **자동 복구가 불가능**하다 |
| P0 | 서비스 중단급 — 부팅 실패·크래시 루프 | 사용자가 접속 자체를 못 한다 |
| P0 | 프로세스 수준 예외 | 다음 요청부터 상태가 어긋난다 |
| P1 | 외부 의존 장애 — DB·Redis·스토리지 | 기능 일부가 죽는다 |
| P1 | 핵심 플로우 실패 — 이 서비스에선 **동화 제작** | 제작 실패가 곧 서비스 실패다 |
| P1 | 배포 결과 | 장애 원인 추적의 출발점 |
| P2 | 보안 — 무차별 로그인 시도 | 즉시성은 낮지만 패턴을 봐야 한다 |

### 보내지 않는다

| 무엇 | 왜 |
|---|---|
| 개별 4xx | 사용자 실수다. 사람이 할 일이 없다 |
| 정상 요청·성공 이벤트 | 알림 피로의 주범 |
| **외부 API 요청·응답 본문** | 루트 [`CLAUDE.md`](../CLAUDE.md) Never |
| **스택 트레이스** | 내부 경로·구조가 외부 채널로 나간다. 로그에 남기고 알림은 "무엇이 어디서" 까지만 |
| **개인정보** — `loginId`·얼굴 이미지 URL·세션 소유자 | Discord 는 외부 서비스다. 채널 권한이 곧 접근 통제가 된다 |
| 중복 억제 없는 반복 | 레이트리밋에 걸려 **정작 중요한 알림이 유실된다** |

## 알림을 추가하는 법

```ts
constructor(@Inject(NOTIFICATION_PORT) private readonly notifications: NotificationPort) {}

this.notifications.notify({
  severity: 'warning',
  title: '무엇이 일어났는가',
  summary: '다음에 무엇을 해야 하는가',
  context: { 상태코드: 502, 건수: 12 },   // 🚫 개인정보·외부 API 본문 금지
  dedupeKey: 'my-feature:some-event',
  dedupeTtlSeconds: 300,
});
```

체크리스트:

- [ ] 이 알림을 받은 사람이 **할 일이 있는가?** 없으면 로그로 바꾼다
- [ ] `summary` 가 **다음 행동**을 말하는가? "실패했습니다" 만으로는 부족하다
- [ ] `context` 에 개인정보·외부 API 본문·스택이 없는가?
- [ ] `dedupeKey` 가 있는가? **레플리카가 3개라 없으면 3번 간다**
- [ ] TTL 이 사건 성격에 맞는가? 자동 복구되지 않는 것은 길게(1시간), 일시적인 것은 짧게(5~10분)

### 설계상 알아 둘 것

- **`notify()` 는 `void` 를 돌려준다.** 일부러 그렇게 했다 — 호출측이 `await` 하면 알림 채널 지연이 도메인 API 지연이 된다. 전송 실패는 전부 삼키고 로그만 남는다.
- **중복 억제는 Redis `SET NX EX`** 다. 레플리카 셋이 같은 사건을 각각 감지하므로 첫 하나만 통과시킨다.
- **Redis 가 죽으면 그냥 보낸다(fail-open).** 장애 알림이 Redis 장애 때문에 사라지는 것이 최악이다 — 중복 3건이 유실 1건보다 낫다.
- 전송 타임아웃 5초. 알림이 5초 안에 못 가면 이미 늦었다.

### 500 을 어떻게 다루는가 — 개별이 아니라 두 신호로

🚫 **개별 500 마다 알리지 않는다.** 같은 버그 하나가 수십 건을 만들어 채널을 덮고, 그러면 크레딧 부족 같은 진짜 알림을 놓친다. 대신 성격이 다른 두 신호로 나눈다.

| 신호 | 무엇을 말하나 | 억제 |
|---|---|---|
| **새 서버 오류** | "이 경로에서 처음 났다" — 배포 직후 새 버그를 잡는다 | 경로별 6시간 |
| **서버 오류 급증** | "지금 서비스가 나쁘다" — 5분에 10건 | 창마다 1회 |

- **절대 건수**로 센다. 에러율(%)은 트래픽이 적을 때 요동친다 — 2건 중 1건이면 50% 지만 사람이 할 일은 없다.
- **경로는 라우트 패턴**(`POST /sessions/:id/pages`)만 쓴다. 🚫 실제 URL 은 세션 ID 를 품어 고카디널리티이자 개인 식별 정보가 된다.
- **4xx 는 세지 않는다**(사용자 실수). **헬스체크 503 도 세지 않는다** — readiness 실패는 passthrough 로 빠지므로 자동 제외된다.
- 카운터는 **Redis**. 레플리카 3개가 각자 세면 실효 임계치가 3배가 된다.
- ⚠️ **집계가 응답을 막지 않는다.** 전역 필터가 `void` 로 부르고 모니터가 모든 실패를 삼킨다 — 에러 응답을 돌려주는 길목이라 여기서 지연되면 장애가 두 배로 보인다.

### ⚠️ `uncaughtException` 리스너는 Node 의 기본 동작을 끈다

**리스너를 등록하는 것만으로 "예외 시 프로세스 종료" 가 사라진다**(Node 22 실측). 그대로 두면 상태가 깨진 프로세스가 계속 요청을 받는다 — 죽는 것보다 나쁘다. 그래서 두 이벤트를 다르게 다룬다:

| 이벤트 | 종료하나 | 왜 |
|---|---|---|
| `uncaughtException` | **한다** (알림 유예 3초 후 `exit(1)`) | 동기 스택이 끊긴 것이라 상태를 믿을 수 없다. 레플리카 3개 + Swarm `restart_policy` 가 받아 준다 |
| `unhandledRejection` | 하지 않는다 | 대개 비동기 체인 하나가 국소적으로 끊긴 것이다. 이것으로 전체를 내리면 가용성이 더 나빠진다 |

🚫 이 정책을 바꾸려면 `process-error-notifier.service.spec.ts` 의 두 테스트(`⭐`)를 먼저 읽는다.
